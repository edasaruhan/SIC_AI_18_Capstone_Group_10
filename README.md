# BeforeScroll

**BeforeScroll** is a capstone-project prototype for exploring how a context-aware early-warning system could help people notice potentially unhelpful phone-use patterns before a long session begins. It combines a synthetic mobile-app usage dataset, a small machine-learning pipeline, and an interactive web dashboard.

## What it does

The web dashboard presents a simulated user's usage patterns and includes:

- A **risk score** and low, medium, or high risk status.
- An early-warning countdown based on the configured prediction horizon.
- An hourly usage trend and the busiest time of day.
- A simulated checklist of daily responsibilities. The selected responsibility state changes the model's risk threshold and prediction context.
- A weekly view of sessions labeled as risky, plus a daily check-in and focus streak.
- A small rule-based assistant with suggested questions and responses.
- Light, dark, and automatic theme options, as well as a responsive layout.

The interface is currently written in Turkish. The source code and this documentation are primarily in English and Turkish.

## How it works

The project has two related workflows:

1. **Dashboard (`app.py`)**: creates a synthetic dataset, builds historical features, trains the demonstration models, and serves the dashboard and API. Model training happens when the server starts, so the first launch can take a few seconds.
2. **Offline experiment (`main.py`)**: simulates data, builds features, evaluates models, and writes CSV outputs. An optional horizon sweep compares several warning lead times.

### Simulation and labels

`simulate.py` generates application sessions for a configurable set of simulated users and days. The simulator models app categories, notifications, app openings, session duration, time-of-day patterns, and whether daily responsibilities have been completed. The risk label is rule-based and applies to selected simulated apps. It uses different duration thresholds depending on whether responsibilities are still pending or complete, with a small configurable amount of label noise.

### Features and models

`features.py` builds time-aware features from completed past sessions and calendar/context information. Its intent is to avoid using information from the future session being predicted. Features summarize activity over recent time windows and include personal-baseline and responsibility-state signals.

`model.py` evaluates a scaled logistic-regression baseline and a histogram gradient-boosting classifier. It uses chronological train/validation/test splits and reports metrics including AUPRC, ROC AUC, precision, recall, and F1. The dashboard uses the histogram gradient-boosting model. The evaluation and reported metrics are based on the synthetic data generated by this project, not on real-world validation.

## Requirements

- Python 3.11 or newer (the Docker image uses Python 3.11).
- `pip`.
- Docker and Docker Compose, if using the containerized setup.

Python dependencies are listed in `beforescroll/requirements.txt`: NumPy, pandas, scikit-learn, and Flask.

## Run locally

From the repository root, install the dependencies and start the Flask server:

```bash
cd beforescroll
python -m venv .venv
```

Activate the virtual environment:

```bash
# macOS / Linux
source .venv/bin/activate

# Windows PowerShell
.venv\Scripts\Activate.ps1
```

Then install the packages and launch the app:

```bash
pip install -r requirements.txt
python app.py
```

Open [http://localhost:8000](http://localhost:8000) in your browser. The server generates simulated data and trains its model on startup. Stop it with `Ctrl+C`.

## Run with Docker

Run these commands from the `beforescroll` directory, where the Dockerfile and Compose file are located:

```bash
cd beforescroll
docker compose up --build web
```

Then visit [http://localhost:8000](http://localhost:8000). The Compose configuration mounts `./output` so generated experiment results can be retained on the host.

To run the offline experiment and horizon sweep in the training container:

```bash
docker compose --profile train run --rm train
```

## Generate data and evaluate models

Run the experiment CLI from `beforescroll`:

```bash
cd beforescroll
python main.py
```

By default, this simulates 40 users over 28 days using a 10-minute warning horizon and writes results to `output/`. The command prints dataset and model evaluation summaries. To also compare 1-, 5-, 10-, and 30-minute horizons:

```bash
python main.py --sweep
```

The main options are:

| Option | Default | Description |
| --- | ---: | --- |
| `--users` | `40` | Number of simulated users. |
| `--days` | `28` | Number of simulated days per user. |
| `--horizon` | `10` | Warning horizon in minutes for feature generation. |
| `--seed` | `42` | Random seed for reproducible simulation and evaluation. |
| `--out` | `output` | Directory in which CSV files are written. |
| `--sweep` | off | Evaluate the 1-, 5-, 10-, and 30-minute horizons. |

Example with custom settings:

```bash
python main.py --users 80 --days 35 --horizon 5 --seed 7 --out output --sweep
```

Generated files include `sessions.csv`, `features_h<horizon>.csv`, and, when `--sweep` is enabled, `horizon_sweep.csv`.

## Web dashboard and API

The Flask application serves the page at `/` and provides these endpoints:

| Method | Endpoint | Purpose |
| --- | --- | --- |
| `GET` | `/api/state` | Get the current simulated dashboard state. |
| `POST` | `/api/tasks` | Update a task checkbox. JSON body: `{"i": 0, "done": true}`. |
| `POST` | `/api/checkin` | Record a daily check-in. JSON body: `{"ok": true}`. |
| `POST` | `/api/ask` | Ask one of the dashboard's suggested questions. JSON body: `{"q": "..."}`. |

Example request:

```bash
curl http://localhost:8000/api/state
```

The task, check-in, and assistant interactions are in-memory demo behavior. They are not persisted to a database.

## Configuration

Default simulation and risk-rule values live in `config.py`. The `Config` dataclass sets the number of users and days, seed, output directory, and warning horizon. The same file also contains the simulated app definitions, time-of-day session rates, risk-label thresholds, and feature windows.

You can change experiment parameters through `main.py` command-line options. The dashboard currently instantiates the default configuration when its `Engine` starts.

## Data and privacy

All sessions are generated locally by the simulator; the repository's dashboard does not request access to a user's phone or import personal usage history. Running the application does not make the generated sample representative of actual people. Treat generated CSVs as experimental artifacts, and do not interpret a demo risk score as a diagnosis or as a substitute for professional guidance.

## Known limitations

- The application is a prototype, not a production-ready monitoring or intervention system.
- Inputs and labels are synthetic and partly rule-defined, so evaluation metrics do not establish real-world predictive performance.
- There is no mobile app integration, persistent user account, database, or durable storage for dashboard interactions.
- Dashboard labels and assistant messages are primarily Turkish and use fixed demo prompts and responses.
- The warning and intervention behavior is illustrative; it should be independently validated and reviewed before any real-world use.
